Explain an application-firewall rejection to browsers or clients. A web application firewall (WAF) makes the blocking decision; its `blocking_page` supplies the response body. Use this behavior for a security rejection, rather than a direct route reply.

| Body | Choose it for | Measured limitation |
| --- | --- | --- |
| Hypertext Markup Language (HTML) | A readable browser rejection page | A benign request remains available. |
| JavaScript Object Notation (JSON) | A structured message for clients | The example's parseable body was served as `text/html; charset=UTF-8`. |

## Attach the selected firewall

Configure `blocking_page` on a firewall in blocking mode, then attach that firewall to the load balancer through `app_firewall`. Both body alternatives use this relationship; select the matching firewall name and namespace.

```

The encoded `blocking_page` value has a 4,096-character limit including the prefix. See [response-body encoding](../configuration-reference/#response-body-encoding) to create your own message.

## HTML blocking page

> **Visitor message:** Request not accepted

```

**Expected result:** A blocked request returns `403` with the readable page; a benign request still reaches the origin. Check the firewall event: a `403` response alone does not prove the WAF made the block decision.

**Verified live example:** [View the HTML WAF block](https://cr-waf-html.f5-sales-demo.com/?q=%27%20OR%201%3D1%20--). The matching enforced WAF event confirms ownership.

**Observed media type:** XC served this parseable JSON body as `text/html; charset=UTF-8`. Check whether your client accepts that media type.
