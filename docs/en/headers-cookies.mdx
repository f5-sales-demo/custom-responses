Choose the scope for response metadata changes: host-wide transformations affect the load balancer, while route-specific headers affect only matching paths. Both can preserve the application body.

## Host-wide headers and cookies

> **Visitor response:** `x-showcase: custom-responses` and a `showcase=custom-responses` cookie, without `x-origin-remove` or `origin-remove`.

Configure the add and remove lists under the load balancer's `more_option` field. The added header uses `append: false`. The cookie has path `/`, Secure, HttpOnly, SameSite Lax, and `overwrite: true`. Check name collisions before overwriting origin values. Adding a cookie here does not sign a user in.

## Route-specific headers

For metadata confined to one path, `/demo/headers` adds `X-CR-Route: scoped` under the route's `advanced_options`. The root response omits this header. The existing host-wide transformations still apply to both responses.

**Verified live example:** [Open the scoped-header route](https://custom-responses.f5-sales-demo.com/demo/headers).

The different controls reflect scope: use an untransformed host for host-wide settings and a nonmatching path on the same host for route settings. See [CORS](../cors/) for browser permission to read a cross-origin response.
