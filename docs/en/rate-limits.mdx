Explain a genuine request-limit rejection while preserving `429`. User identification groups synthetic clients by the `X-CR-Client` header and limits GET requests to exactly `/demo/rate-limit`.

> **Visitor response:** Demo request limit reached

The header is a demonstration identity; callers can change it. It does not authenticate clients or define a production identity design.

## Connect identification, limiter and response

## Trigger and interpret the rejection

The focused widget sends seven fixed GET requests using a fresh synthetic client. It runs only when clicked, reserves fourteen requests including possible preflights, caps a page visit at 36 requests, and allows a run at most once per two minutes.

<iframe src="../../assets/rate-limit-demo.html" title="Bounded request-limit demonstration" loading="lazy" style="width:100%;height:40rem;border:0;border-radius:0.5rem" />

1. Select **Trigger custom 429**.
2. Compare the first five successful responses with the later `429` responses and custom body.

**Expected result:** The selected requests exceed the allowance and receive `429` with “Demo request limit reached”. A different synthetic client, POST request or unrelated path still reaches the origin. The measured API Rate Limiting event identifies the limiter as the block owner; the status alone does not.

The ten-second block duration is distinct from replenishing the request allowance. Recovery was measured after 65 seconds. The widget's two-minute cooldown bounds repeated demonstrations; it does not measure recovery, and loading it sends no test requests.

**Verified live example:** [Open the rate-limit endpoint](https://cr-response-controls.f5-sales-demo.com/demo/rate-limit). A single navigation does not demonstrate exceeding the allowance.
